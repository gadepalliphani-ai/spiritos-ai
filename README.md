## Quick Start

### 1. Install Rust (nightly)

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --default-toolchain nightly
source "$HOME/.cargo/env"
rustup target add x86_64-unknown-none aarch64-unknown-none-softfloat
rustup component add rust-src llvm-tools-preview
```

### 2. Install QEMU

```bash
# macOS
brew install qemu

# Ubuntu/Debian
sudo apt-get install -y qemu-system-x86 qemu-system-arm
```

### 3. Clone and Build

```bash
git clone https://github.com/gadepalliphani-ai/spiritos-ai.git
cd spiritos-ai
```

**Build x86_64:**
```bash
cd crates/spiritos-x86_64
cargo build \
  -Z build-std=core,compiler_builtins \
  -Z build-std-features=compiler-builtins-mem \
  --target x86_64-unknown-none
```

**Build aarch64:**
```bash
cd crates/spiritos-aarch64
cargo build \
  -Z build-std=core,compiler_builtins \
  -Z build-std-features=compiler-builtins-mem \
  --target aarch64-unknown-none-softfloat
```

### 4. Run in QEMU

**x86_64:**
```bash
qemu-system-x86_64 \
  -kernel target/x86_64-unknown-none/debug/spiritos-x86_64 \
  -serial stdio -display none -no-reboot -m 128M
```

**aarch64:**
```bash
qemu-system-aarch64 \
  -M virt -cpu cortex-a53 -m 128M \
  -kernel target/aarch64-unknown-none-softfloat/debug/spiritos-aarch64 \
  -serial stdio -display none -no-reboot
```

Expected output:
```
[spiritos] Kernel starting...
[spiritos] Memory OK
[spiritos] Scheduler OK
[spiritos] Drivers OK
[spiritos] Interrupts enabled
[spiritos] SpiritOS.ai v0.2 - context switching active
[rt] scheduler: round-robin preemptive, tick=100Hz
[rt] latency: QEMU smoke-test only; hard RT requires hardware measurement
[rt] context-switch: task 'hello' running
[rt] context-switch: task 'hello' running
...
[rt] timer tick (100 Hz, ...)
```

## Checking Real-Time Properties

SpiritOS targets hard real-time behaviour with a preemptive round-robin scheduler ticking at **~100 Hz** (10 ms period). This section explains how to observe and verify those properties.

### What the kernel emits

The kernel writes structured log lines to the serial port that can be used for RT verification:

| Log prefix | Meaning |
|---|---|
| `[spiritos] Scheduler OK` | Scheduler initialised; tasks queued |
| `[rt] scheduler: round-robin preemptive, tick=100Hz` | Scheduler type and tick rate |
| `[rt] timer tick (100 Hz, ...)` | Timer ISR fired; emitted every 10 ticks (~100 ms) |
| `[rt] context-switch: task 'hello' running` | Task resumed after context switch |
| `[rt] latency: QEMU smoke-test only; ...` | Explicit CI-vs-hardware disclaimer |

### Verifying timer tick cadence in QEMU

Capture serial output and count tick lines over a known wall-clock window:

```bash
# Capture 5 seconds of output
timeout 5 qemu-system-aarch64 \
  -M virt -cpu cortex-a53 -m 128M \
  -kernel target/aarch64-unknown-none-softfloat/debug/spiritos-aarch64 \
  -serial stdio -display none -no-reboot 2>&1 | tee boot.log

# Count tick messages (expect ~5 in 5 s, since one is emitted per 10 ticks @ 100 Hz)
grep -c "\[rt\] timer tick" boot.log

# Show context-switch events
grep "\[rt\] context-switch" boot.log | head -20
```

Expected: roughly 1 tick message per 100 ms (10 ticks × 10 ms each). QEMU timing is **not monotonic** and will vary with host load; treat these counts as order-of-magnitude checks.

### Verifying scheduler tick cadence

The scheduler fires on every timer IRQ. To observe scheduling decisions:

```bash
grep "\[rt\]" boot.log
```

You should see an interleaved pattern of timer ticks and context-switch events, confirming preemption is happening.

### Verifying context-switch activity

Each time the demo task is resumed after a preemption, it logs:
```
[rt] context-switch: task 'hello' running
```

Multiple occurrences confirm that:
1. The timer ISR is firing.
2. The scheduler is picking a next task.
3. The architecture-specific `switch_to` (register save/restore) is working.

### Checking latency bounds

> ⚠️ **QEMU is not suitable for latency measurement.** QEMU virtualises time and introduces variable overhead from the host OS scheduler. Do not draw conclusions about worst-case interrupt latency from QEMU numbers.

For latency measurement on **real hardware** (e.g., Raspberry Pi 4):

1. **Oscilloscope method**: Toggle a GPIO pin at the start and end of the timer ISR; measure the period with a logic analyser or oscilloscope.
2. **Cycle counter method**: Read `CNTPCT_EL0` at ISR entry and at the end of context switch; compute the difference.
3. **Dedicated RT benchmarks**: Tools like [`cyclictest`](https://wiki.linuxfoundation.org/realtime/documentation/howto/tools/cyclictest/start) (for Linux), or a custom spin-wait loop measuring tick jitter.

SpiritOS does not yet include built-in latency instrumentation. Contributions welcome — see [Contributing](#contributing).

### What CI validates vs. what requires hardware

| Property | CI (QEMU) | Hardware required |
|---|---|---|
| Kernel boots and initialises | ✅ Yes | — |
| Scheduler init message present | ✅ Yes | — |
| Timer fires (log markers appear) | ✅ Smoke test | — |
| Context switches execute | ✅ Smoke test | — |
| Tick period is ~10 ms | ❌ Unreliable in QEMU | ✅ Oscilloscope / cycle counter |
| Worst-case interrupt latency | ❌ Not measurable | ✅ Logic analyser on hardware |
| Jitter < 1 µs (hard RT claim) | ❌ Cannot verify | ✅ Dedicated RT benchmark |

**The CI checks are regression tests, not RT certification.** They catch regressions (broken boot, missing scheduler, silent timer) but cannot prove timing guarantees.
